# NXTSight — on-device pipeline dependencies
# Target runtime: whatever real accelerator ONNX Runtime finds on this
# machine — Snapdragon NPU (QNN), NVIDIA GPU (CUDA), Windows GPU (DirectML),
# or Apple Neural Engine/GPU (CoreML) — CPU always as the universal
# fallback. See src/pipeline/runtime.py for the priority order and honest
# per-vendor testing notes.
#
# Every version below is pinned exactly (captured from a real working
# install, not guessed) so that `pip install -r requirements.txt` gives
# everyone the same environment instead of quietly resolving to whatever
# is newest on the day they happen to install it. If you need to bump a
# version, do it deliberately, re-run the full test suite, and re-pin —
# don't just delete the "==".
#
# Nothing in this file requires a Qualcomm AI Hub account, a network call,
# or any Snapdragon-specific tooling — `pip install -r requirements.txt`
# then `streamlit run app.py` runs entirely on whatever hardware ONNX
# Runtime finds locally. qai-hub (the raw SDK used to submit real
# compile/profile jobs to Qualcomm's cloud) and qai-hub-models (needed for
# one optional export CLI, and for pulling in plain `opencv-python`, which
# silently conflicts with the `opencv-python-headless` that easyocr needs
# below — both install a `cv2` package at the same path) are both
# deliberately left out of this base install. They're an optional extra
# for squeezing out real, measured Snapdragon-specific performance later
# (see the "Snapdragon / Qualcomm AI Hub" section in README.md) — install
# them yourself, separately, only if you're actually compiling for
# Snapdragon or running that one export command:
#     pip install qai-hub qai-hub-models

# On-device inference runtime. onnxruntime-qnn ships ONNX Runtime with the
# QNN execution provider, which is how a compiled model actually reaches the
# Snapdragon Hexagon NPU — but it only publishes Windows/Linux-ARM wheels,
# and its version numbers do NOT track plain onnxruntime's (it's on its own
# 1.20.x/2.x line). Everywhere else (this dev Mac included) we install
# plain onnxruntime — which already ships CUDA/DirectML/CoreML execution
# providers for the platforms that support them, no extra package needed —
# and src/pipeline/runtime.py auto-detects at startup which real
# accelerator is actually present, falling back to CPU if none are. The
# onnxruntime-qnn pin below is UNVERIFIED on this machine (no Windows/ARM
# hardware to test on) — if it fails to install or import on the real
# Snapdragon device, check https://pypi.org/project/onnxruntime-qnn/ for
# the current version list and adjust.
onnx==1.19.1  # newer onnx defaults to an IR version this onnxruntime can't load
onnxruntime==1.19.2; sys_platform != "win32"
onnxruntime-qnn==1.20.0; sys_platform == "win32"

# Screenshot OCR (feature 1: scam message detection from a screenshot).
# EasyOCR is pure-Python (no system Tesseract binary required) so it runs

# this was tested against, not whatever's newest that day.

# IMPORTANT for judges on a real Snapdragon Windows PC: torch==2.2.2 (like
# every torch version checked, through 2.11.0) has NO win_arm64 wheel on
# PyPI — confirmed directly with `pip download --platform win_arm64`, not

# distribution"). Fix: install the regular 64-bit (x64/AMD64) Python
# instead — Windows 11 on ARM runs it via built-in emulation, torch's
# win_amd64 wheel installs and runs fine, and Qualcomm ships an
# onnxruntime-qnn win_amd64 wheel too (confirmed downloadable), so QNN/NPU
# access should still work from an x64 Python process — genuinely NOT
# verified end-to-end on physical Snapdragon hardware from this dev
# machine, unlike the AI Hub compile+profile jobs elsewhere in this
# project, which did run on real Snapdragon silicon (in Qualcomm's cloud
# device farm, not locally). Test this combination on real hardware before

# Call Shield speech-to-text (feature 4: scam-call detection from an
# uploaded recording). Whisper's own audio loader shells out to a system
# `ffmpeg` binary for most formats, which isn't installed on every machine
# (this dev Mac included, no Homebrew either) — so src/pipeline/stt.py
# decodes WAV files itself (stdlib `wave` + numpy, already a dependency
# above) and only uses Whisper for the actual transcription, sidestepping
# the ffmpeg dependency entirely. Already reuses torch, pinned above.
#
# numba is pinned explicitly even though we never import it ourselves:
# openai-whisper depends on it with NO version constraint at all, so pip
# picks whatever's newest — which pulls in a newer llvmlite than 0.43.0,
# the last version with an Intel-Mac wheel (same story as the torch pin
# above). Without this pin, `pip install -r requirements.txt` tries to
# compile llvmlite from source on Intel Macs and fails outright unless a
# full LLVM toolchain happens to be installed. Confirmed reproducible on a
# genuinely clean venv, not a one-off — this isn't hypothetical.
numba==0.60.0
openai-whisper==20250625

# Optional, faster middle tier ahead of the plain-PyTorch fallback above:
# whisper.cpp (GGUF), via the pywhispercpp binding, gives Call Shield real
# hardware acceleration (Metal / CUDA / Vulkan, auto-detected by ggml at
# build time) on machines that have no Snapdragon NPU — this dev Mac
# included, which previously ran speech-to-text on pure CPU PyTorch and
# now genuinely uses Metal. Deliberately NOT pinned/installed here: it's
# optional (src/pipeline/whisper_cpp.py degrades to the PyTorch fallback
# above if it's missing), and getting Metal/CUDA/Vulkan support means
# building from source, which needs a C++ toolchain (already present via
# Xcode Command Line Tools on this Mac) and `cmake` (not preinstalled
# here — pip install it, don't assume Homebrew):
#     pip install cmake
#     pip install pywhispercpp==1.5.1 --no-binary pywhispercpp
# CONFIRMED, REPRODUCIBLE macOS-only bug in that source build: the
# compiled .dylib/.so files get an install-time rpath pointing at pip's
# temporary build directory, which is deleted right after — every file
# actually lands correctly in site-packages, the rpath just points
# nowhere. Reproduced twice in a row on this machine, not a one-off.
# Fix (safe to re-run, no-ops if already fixed):
#     python scripts/fix_pywhispercpp_macos.py

# Local LLM second opinion for Scam Shield and Money Insight (scam_detection
# and spend_categorization only — Call Shield doesn't use this): when the
# fast MiniLM+head classifier's own confidence is genuinely ambiguous (see
# the llm_escalation_margin comments in src/scam_detector/classifier.py and
# src/spend_categorizer/categorizer.py), engine.py escalates to a small
# local Qwen2.5-1.5B-Instruct model via structured-JSON prompting — never
# on every message, only the unsure ones (measured: ~2.5-9.5s per call on
# this dev machine, so paying that on every message would make the app feel
# broken). Optional: src/pipeline/llm_classifier.py degrades to "no
# escalation, fast-path result only" if either piece below is missing.
#
# 1. The Python binding — same ggml/GGUF ecosystem as pywhispercpp above,
#    same story: the plain PyPI wheel is CPU-only, real GPU offload (Metal
#    on macOS, CUDA on NVIDIA, Vulkan elsewhere) needs a source build:
#        pip install llama-cpp-python==0.3.35
#    That alone already builds Metal support on macOS (ggml enables it by
#    default on Apple platforms, confirmed via a real load — see README).
#    For CUDA specifically, set CMAKE_ARGS before installing:
#        CMAKE_ARGS="-DGGML_CUDA=on" pip install llama-cpp-python==0.3.35 --no-cache-dir
#    Unlike pywhispercpp, this build did NOT hit the same rpath bug on this
#    machine — no separate fixup script needed for this one.
#
# 2. The model weights (~1.07GB, Qwen's own official GGUF export, no
#    license gate, no HuggingFace account needed):
#        mkdir -p models/llm && curl -L -o models/llm/qwen2.5-1.5b-instruct-q4_k_m.gguf \
#          https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF/resolve/main/qwen2.5-1.5b-instruct-q4_k_m.gguf
#    A one-time download, same "needs internet once, fully offline after"
#    pattern as EasyOCR/Whisper's model weights — loaded from that literal
#    local path at runtime, never a HuggingFace repo id, so there's no
#    download-on-first-use behavior for network_guard to catch.
#
# Honest limitation, not a footnote: pip's requirements.txt / environment
# markers can express *platform* conditionals (see onnxruntime-qnn's
# `sys_platform == "win32"` above) but cannot detect *runtime hardware*
# (whether a GPU is actually present) at install time — that's simply
# outside what a requirements.txt file can do. What's conditional here is
# expressed the only way it honestly can be: build flags you choose based
# on your own hardware, documented above, not a magic auto-detecting pip
# install.
