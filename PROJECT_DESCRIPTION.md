# NXTSight — Project Description

## The problem

Roughly **1 in 5 UPI users in India has been targeted by a payment fraud**, and government data shows over **₹805 crore lost to digital payment scams this financial year alone**. These frauds — fake KYC updates, OTP-sharing requests, too-good investment offers, "your account is blocked" threats, fake delivery fees — arrive as plain text messages, and the people most exposed to them are often the least equipped to spot the pattern in the moment. At the same time, most people have no real visibility into where their money actually goes month to month; bank SMS and UPI notifications pile up unread.

NXTSight is a small on-device engine that addresses both: it reads a suspicious message and tells you, in plain language, whether it looks like a scam and why — and it reads your transaction messages and tells you, in plain language, where your money is going. Both run through the same local model-serving pipeline, entirely on the device, with no cloud dependency.

Norton's parent company, Gen Digital, already ships an AI scam detector (Genie) globally — this isn't an empty market. But Genie's own India page says nothing about UPI-specific fraud, fake KYC, digital-arrest calls, or courier-customs scams, and Gen Digital's own numbers show its strength in North America and Europe. That's the gap NXTSight targets: depth in exactly the fraud patterns and payment rails that dominate the Indian market, running fully on-device rather than phoning a server for every check.

## Technical implementation

NXTSight's core is `NXTSightEngine` — one shared object that owns every line of model-serving code (text validation, embedding, hardware-accelerated inference) for all three of its classification tasks: scam detection, spend categorization, and call-scam detection. Each is a small trained head sitting on a shared MiniLM-v2 text embedding, registered as a `Task` on the shared engine, interpreted by its own thin feature module. Verified by a test that checks the feature modules hold the exact same engine object by Python identity, not just similarly-shaped code.

The engine auto-detects real hardware acceleration at startup — Qualcomm's QNN provider (Snapdragon NPU), CUDA (NVIDIA GPU), DirectML (Windows GPU), or Apple's CoreML — and falls back to plain CPU if none are present, with zero code change and zero crash either way. This isn't a claim — it's a live, on-screen badge in the demo, proven in the automated test suite for every path: real hardware where this project has access to it (Apple Neural Engine), the real production model run end-to-end under every other path (Snapdragon NPU, NVIDIA GPU, Windows GPU) with the hardware itself simulated, stated plainly as exactly that rather than blurred into a claim of physical verification. Screenshot OCR (EasyOCR) and Call Shield's speech-to-text (Whisper) both go through the same accelerated path today, with their own compiled-and-profiled real Snapdragon hardware numbers from Qualcomm AI Hub (38.1ms / 20.4ms for OCR's two stages, 27.8ms for Whisper's encoder) as additional, optional proof beyond the vendor-neutral default every model already ships.

Two features — Scam Shield and Money Insight — go a step further: when the fast classifier's own confidence is genuinely ambiguous, the engine escalates to a local 1.5B-parameter LLM (Qwen2.5-1.5B-Instruct, quantized, via `llama-cpp-python`) for a structured second opinion, never on every message — a real, measured latency cost of a few seconds is worth paying only when the fast path is actually unsure. The calling code for both features has zero knowledge any of this exists; it calls one interface and gets back a verdict, whether that verdict came from an ONNX session on a Snapdragon NPU, a CPU fallback, or the LLM.

The project also demonstrates genuine offline capability, not just an offline-sounding pitch: a network guard patches the process's socket layer so any outbound connection is blocked, then the app makes a real connection attempt against itself at every startup and confirms its own code rejected it. The whole pipeline is backed by **178 automated tests**, including a 40-example adversarial stress test of the scam classifier (zero missed scams), a crash-proofing audit that feeds malformed/hostile input through every function, and exact-pinned dependencies with a "doctor" script that gives actionable errors instead of cryptic failures on a new machine.

## Application use case & innovation

Most fraud-detection tools are cloud services: they see your messages, they need connectivity, and they cost money per query. NXTSight is built the opposite way — the message never leaves the device, it works with no signal at all, and there's no recurring inference cost. That matters specifically for the population most exposed to UPI fraud: users with intermittent connectivity, users wary of sending personal financial messages to a third-party server, and users for whom a subscription-gated safety feature simply isn't viable.

The innovation isn't any one model — it's the shared engine and its hardware-agnostic interface. Scam detection, spend categorization, and call-scam detection are three tasks plugged into one on-device NLP layer, the same way a single background service on a real phone (in the mold of Walnut or Money View, which already read SMS automatically in India today) would serve all three from the same stream of incoming messages, without duplicating the on-device footprint per feature. Because the calling code never touches hardware directly, the same engine could serve predictions from inside a fintech's own backend later, not just as a standalone app on one device — the interface doesn't change whether it's running on a phone, a Snapdragon PC, or a server. The demo UI's manual upload/paste is explicitly labeled a demo simplification — the intended product reads incoming SMS and notifications automatically, with the user never opening an app or typing anything.

## Deployment & accessibility

No login, no account, no cloud backend to provision or pay for. Setup is `pip install -r requirements.txt` and `streamlit run app.py`; a bundled `check_setup.py` doctor script checks the Python version and every dependency before the app even starts, giving an exact fix command instead of a cryptic failure — verified by actually simulating a broken environment and confirming the error message, not just writing it and hoping. Because CPU is always a fallback, the app runs on ordinary hardware today; on a machine with a Snapdragon NPU, an NVIDIA or Windows GPU, or an Apple Neural Engine, it automatically gets faster inference with no configuration — Snapdragon is the fastest path this project has measured, not the only one it runs on. Every dependency version is pinned exactly, so an install today behaves the same as an install six months from now; the handful of genuinely optional, hardware-accelerated extras (Qualcomm AI Hub's compiled models, whisper.cpp, the local LLM) are each documented as exactly that — real performance upside, never a requirement to run the app at all.

## Presentation & documentation

The README is written for a stranger with zero context to clone the repo and get it running on the first try — exact commands, exact things to click, sample data bundled so there's nothing to hunt for. Every claim central to the pitch (on-device only, real hardware acceleration, no network) is backed by an on-screen, self-verifying indicator in the live demo rather than asserted in slides, and every known limitation — which hardware paths are genuinely physical-chip-tested versus simulated, where a tiny model still occasionally misreads a genuinely novel case, the real latency cost of the LLM escalation tier — is documented plainly instead of glossed over. An unstated gap costs trust in everything else claimed; an honest limitation, written down before anyone has to go looking for it, earns it back.
