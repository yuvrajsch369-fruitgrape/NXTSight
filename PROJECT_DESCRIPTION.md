# NXTSight — Project Description

## The problem

Roughly **1 in 5 UPI users in India has been targeted by a payment fraud**, and government data shows over **₹805 crore lost to digital payment scams this financial year alone**. These frauds — fake KYC updates, OTP-sharing requests, too-good investment offers, "your account is blocked" threats, fake delivery fees — arrive as plain text messages, and the people most exposed to them are often the least equipped to spot the pattern in the moment. At the same time, most people have no real visibility into where their money actually goes month to month; bank SMS and UPI notifications pile up unread.

NXTSight is a small on-device engine that addresses both: it reads a suspicious message and tells you, in plain language, whether it looks like a scam and why — and it reads your transaction messages and tells you, in plain language, where your money is going. Both run through the same local model-serving pipeline, entirely on the device, with no cloud dependency.

## Technical Implementation

NXTSight's core is `NXTSightEngine` — one shared object that owns every line of model-serving code (text validation, TF-IDF vectorization, ONNX Runtime session management) for both features. Each feature is a small TF-IDF + Logistic Regression classifier exported to ONNX, registered as a `Task` on the shared engine, and interpreted by its own thin feature module. This isn't two apps that happen to share a UI — it's one on-device inference layer doing two jobs, verified by a test that checks both feature modules hold the exact same engine object by Python identity, not just similarly-shaped code.

The engine auto-detects Qualcomm's QNN execution provider at startup: on a Snapdragon Windows PC with `onnxruntime-qnn` installed, both classifiers run on the Hexagon NPU; anywhere else, they fall back to CPU automatically, with zero code change and zero crash. This isn't a claim — it's a live, on-screen badge in the demo, and it's proven in the automated test suite. Separately, the OCR stage's EasyOCR model was compiled for the Snapdragon X Elite via Qualcomm AI Hub and profiled on real physical Snapdragon hardware in Qualcomm's cloud device farm: genuine measured numbers, 38.1ms (detector) and 20.4ms (recognizer) — proof this runs at NPU speed, with that compiled model as the next integration step into the live OCR call.

The project also demonstrates genuine offline capability, not just an offline-sounding pitch: a network guard patches the process's socket layer so any outbound connection is blocked, then the app makes a real connection attempt against itself at every startup and confirms its own code rejected it — turning "works with wifi off" into something the app proves about itself live, rather than something claimed out loud. The whole pipeline is backed by 86 automated tests, including a 47-example adversarial stress test of the scam classifier (zero missed scams), a crash-proofing audit that feeds malformed/hostile input through every function, and exact-pinned dependencies with a "doctor" script that gives actionable errors instead of cryptic failures on a new machine.

## Application Use Case & Innovation

Most fraud-detection tools are cloud services: they see your messages, they need connectivity, and they cost money per query. NXTSight is built the opposite way — the message never leaves the device, it works with no signal at all, and there's no recurring inference cost. That matters specifically for the population most exposed to UPI fraud: users with intermittent connectivity, users wary of sending personal financial messages to a third-party server, and users for whom a subscription-gated safety feature simply isn't viable.

The innovation isn't the individual models — it's the shared engine. Scam detection and spend categorization are framed as two tasks plugged into one on-device NLP layer, the same way a single background service on a real phone (in the mold of Walnut or Money View, which already read SMS automatically in India today) would serve both a fraud alert and a spending summary from the same stream of incoming messages, without duplicating the on-device footprint for each feature. The demo UI's manual upload/paste is explicitly labeled a demo simplification — the intended product reads incoming SMS and notifications automatically, with the user never opening an app or typing anything.

## Deployment & Accessibility

No login, no account, no cloud backend to provision or pay for. Setup is `pip install -r requirements.txt` and `streamlit run app.py`; a bundled `check_setup.py` doctor script checks the Python version and every dependency before the app even starts, giving an exact fix command instead of a cryptic failure — verified by actually simulating a broken environment and confirming the error message, not just writing it and hoping. Because CPU is always a fallback, the app runs on ordinary hardware today; on a Snapdragon-powered device it automatically gets faster, lower-power inference with no configuration. Every dependency version is pinned exactly, so an install today behaves the same as an install six months from now.

## Presentation & Documentation

The README is written for a stranger with zero context to clone the repo and get it running on the first try — exact commands, exact things to click, sample data bundled so there's nothing to hunt for. Every claim central to the pitch (on-device only, NPU vs. CPU, no network) is backed by an on-screen, self-verifying indicator in the live demo rather than asserted in slides, and every known limitation (OCR not yet on the NPU path, a tiny model's occasional misclassification on a genuinely novel merchant name) is documented plainly instead of glossed over — because a judge who finds an unstated gap trusts the rest of the claims less, and one who reads an honest limitation trusts the rest of the claims more.
